# 圖片順序輸入：立即暫停與原進度恢復

狀態：使用者已確認「只有圖片順序輸入立即暫停」與「長按／等待接續剩餘時間」，並要求修改後打包。已完成實作、獨立審查修正及 Windows 全套測試／打包檢查；原路徑 exe 因仍在執行而尚未替換，詳見實作報告。

## 1. 已確認的需求

- 只對圖片順序輸入新增中途暫停；聊天與其他功能維持原本觸發／動作邊界行為。
- 本機 OCR 確認提示出現後，不等待整個長按、等待或文字動作完成。
- 先停止腳本輸入、放開正在按住的鍵，讓出輸入權，再開始 AI 辨識與答案輸入。
- Discord 文字通知仍在 OCR 命中當下並行啟動，每回合一次，不等暫停完成或 AI 結果。
- 解題並確認提示消失後，長按／等待接續剩餘時間：原定 10 秒、已執行 3 秒，恢復後只做剩餘 7 秒。
- 已送出的文字、點擊與其他不可逆輸入不重播；不從頭重跑目前腳本、迴圈或子腳本。
- F10／停止按鈕、失焦、幾何改變、定位失效、辨識失敗或逾時，都不自動恢复原輸入。
- 補上真正開始監看時的 INFO，包含區域、每秒 OCR 及 Discord 是否已設定；未啟用時不誤報，正常等待不每秒洗版。
- 完成測試後重新打包 exe，備份舊版；直接在目前 `main`、原工作目錄作業，不開分支／worktree，不覆蓋其他修改。

## 2. 現況與需要變動的位置

`Player._run_actions()` 目前只在動作前呼叫 `VisualIntervention`。長按由 Player 掌管，但 `_sleep` 只感知永久 stop_event，不感知圖片暫停。backend 的整段文字、多次點擊、拖曳及短暫 settle 也沒有統一的可恢復暫停介面。

`PanelWatcher`／舊 `SequenceWatcher` 目前 OCR 命中後會立即排入 AI；`requested` 只告知 Player 下次動作邊界要接手。因此必須同時修改「腳本中途檢查」及「AI 等輸入權交接完成才啟動」，不能只提前設 requested 或從背景執行緒送 key-up。

既有 `docs/superpowers/specs/2026-07-09-immediate-stop-design.md` 的永久停止仍保留：F10 不可被此暫停機制清除或重用成 resume。

## 3. 方案取捨

### 採用：Player 擁有的合作式暫停與可恢復執行

沿用目前唯一腳本輸入執行緒。只有啟用圖片順序輸入時，長等待切成至多 20ms 的可中斷等待片段，在原生輸入邊界檢查 requested；按住狀態以明確 release／restore 操作管理。同步呼叫暫停處理，完成後從原本 Python 執行位置接續，不重跑整個動作。

### 不採用：背景執行緒強制放鍵／同時解題

這會與 Player 仍在送出的按鍵競爭，原動作可能在解題期間重新 key-down，無法保持唯一輸入權。

### 不採用：永久停止後重新啟動腳本

會丟失剩餘時間、字元位置及巢狀執行進度，也可能重播已發出的動作。

## 4. 「立即」的定義與限制

以 **OCR 完成有效提示判斷** 為起點，不是面板實際顯示的那一毫秒；每秒取樣與 OCR 自身仍有偵測延遲。

- Player 可中斷的長按／等待，下一個至多 20ms 的合作式檢查點即開始暫停，不等待整個動作時長。
- 文字在單一字元之間、多次點擊在單次點擊之間檢查；原生滑鼠 settle 改為短片段檢查，不能等完後不檢查就送出。
- 清理已按下的鍵／滑鼠按鈕後，才宣告「腳本已暫停」並允許 AI 辨識。
- 已進入作業系統或第三方套件的單次不可取消呼叫不能安全強殺，必須等該呼叫返回。20ms 是程式的檢查片段，不是作業系統硬即時保證。
- 原生 OCR／視窗查詢若正在阻塞，回來後立刻重新檢查暫停與時限；期間不得繞過交接確認而讓另一條執行緒送輸入。超過原有 25／30 秒門檻就停止，不補送。

這一輪不增加通用的「暫停所有功能」按鈕，也不承諾能撤回已經送出的原生輸入。

## 5. 事件與輸入權交接

每個圖片回合有獨立 round ID、requested 狀態及「腳本已放開输入」確認；不以一個永久設定的 Event 授權後續所有回合。

1. OCR 命中：以原影像擷取時間建立回合和截止時間，設 requested，立即派送既有 Discord 文字通知。
2. capture／OCR 持續收集影像，有界緩衝仍有效；**實際面板 AI 請求先等待暫停確認**。
3. Player 在中途檢查點看到 requested，保存目前動作進度並放開本動作持有的鍵／按鈕。
4. 唯一输入執行緒確認視窗、回合、停止旗標、放鍵結果及時限後，交接給 sequence-only 處理入口。這個入口不順便呼叫一般聊天流程。
5. sequence-only 入口向 watcher 確認同一 round ID 已讓出輸入權，AI 才能開始辨識已通過 OCR 的影像。
6. 既有字元收集、固定提交點、Ctrl+A、單次確認及兩次 OCR absent 驗證維持不變。
7. 成功後再次驗證可恢復條件、清除本回合請求，回到原动作的剩餘部分；若失敗則保留永久 stop，不恢復任何 key-down。

新舊圖片順序輸入模式都使用上述交接。新 panel 模式仍無啟動 AI 預檢；舊 manual 模式既有的合成圖預檢不會在腳本輸入期間執行，本次不順帶改變它。

## 6. 執行器與輸入後端的責任

### 6.1 Player／暫停協調元件

新增專用的 sequence 暫停協調邏輯，管理：當前 script/window、暫停請求、當前動作的 release／restore、暫停耗時及中途 sequence-only 呼叫。不可讓此協調元件變成第二個能任意發鍵的背景執行者。

只有主腳本已啟用圖片順序輸入時才接線。未啟用時保持目前動作與 sleep 路徑，避免改變聊天、CLI、規則、測試注入 sleep 的既有語義。

呼叫 sequence-only 處理期間暫時停用「腳本的暫停檢查」，避免答案輸入看到同一 requested 而遞迴暫停；F10、deadline、前景與幾何檢查仍有效。

### 6.2 持續時間

長按、delay、wait_text／wait_image 的剩餘預算不扣除解題暫停時間。使用同一 action 初次計算的亂數／jitter 時長，恢復時不重新抽樣。維持獨立的 action 執行時間計算，**不得調整 watcher 的絕對時鐘或 deadline**。

輸入模式的重複 key-down／scan-pulse 在暫停時停止，恢復後才繼續。保留既有一般、遊戲、Windows 前景訊息及掃描碼脈衝模式。

### 6.3 平台輸入原語

優先沿用 Player 已有 key_down／key_up、key_combo_down／up 與 checked mouse click。針對仍會在內部等待後送輸入的 mouse drag／scroll 增加受檢查的原語，確保暫停／停止已發生時不繼續送出下一段。

所有可能因暫停而中斷的按下操作必須有 `finally` 釋放路徑。平台後端只提供可檢查的原語，不自行啟動 AI、不擁有整體回合、不更改 global stop_event。

## 7. 各動作的暫停與恢復

| 動作 | 暫停時 | 解題成功後 |
| --- | --- | --- |
| 單鍵長按／有時長的組合鍵 | 放開本動作按住的鍵，保留剩餘時長 | 在相同有效目標重新按下，完成剩餘時長，再正常放開 |
| delay | 停止等待並保存剩餘時間 | 接著等剩餘時間，不重新抽亂數 |
| wait_text／wait_image | 停止後續輪詢；已進入的原生辨識返回後不使用過期結果 | 用剩餘 timeout 重新取樣，不沿用暫停前座標或命中結果 |
| text_input | 單一字元送完後不再送下一字元，保留游標進度 | 從下一個未送出的字元接續；不重播已送前綴 |
| 多次 mouse_click | 已送出的單次點擊不重複；下一次點擊前檢查 | 只完成尚未送出的次數，重新確認視窗和座標 |
| 短點按／零時長組合鍵 | 已發出按下就釋放，記為已執行，不為剩餘短 hold 再按一次 | 從下一動作繼續，避免觸發兩次快捷鍵 |
| mouse_move／scroll | 未送出的部分暫停；已送的原生單元不回放 | 只完成未送出的原子操作 |
| click_text／click_image | 判斷與點擊之間也要檢查；暫停會使原命中座標失效 | 重做辨識，且只送尚未送出的那次點擊 |
| mouse_drag | 中途放開滑鼠按鈕，停止後續拖曳 | 若已按下開始拖曳，解題後停止並提示人工確認，不自動重拖；若尚未按下則可重新驗證後開始 |
| loop／run_script／條件分支 | 保存原堆疊及執行位置，不從頂層重跑 | 延續原迭代與分支；暫停前的視覺判斷若尚未產生效果則重新驗證 |

長按的恢复一定會重新 key-down；這是接續按住剩餘時間，不是還原一個物理上從未放開的按鍵。不能保證遊戲不把重新 key-down 視為新的一次按下。

拖曳可能已改變目標程式狀態，無法安全推算「剩餘拖曳」；採取解題後停止的保守例外，不猜測或重播。

## 8. 聊天及其他功能不變

聊天本身不取得立即暫停權；沒有圖片提示時，聊天仍依目前的動作邊界／已存在 preemption 規則執行。

圖片出現時沿用聊天讓出輸入權與取消晚到結果的保護。若聊天草稿已輸入一半，圖片處理完仍依原規則停止，不能因新增 resume 而繼續把遊戲按鍵送进聊天框。

不得由 background OCR／AI、Discord callback 或其他執行緒呼叫 Player 的恢復／輸入原語。

## 9. 日誌

在監看確實啟動後只記錄一次 INFO：

```text
圖片順序輸入：監看已啟動，每秒 OCR 檢查，等待提示出現；區域=(x, y, 寬, 高)；Discord=已設定／未設定
```

另記錄有意義的狀態切換：
- OCR 偵測到提示，正在暫停腳本。
- 腳本已暫停、按鍵已放開，開始 AI 辨識。
- 提示已消失，接續原動作剩餘時間。
- 中止時記錄不恢復的原因。

未啟用、不曾 start、已取消或啟動失敗，不印「已啟動」。重複 start 不重複印；一般等待不每秒刷 INFO。日誌不包含 Webhook、金鑰或截圖；啟動 INFO 本身不發 Discord，也不觸發 AI 預檢。

## 10. 安全與錯誤處理

- 暫停不使用 `stop_event.set()` 後再 clear 的方式，避免吞掉 F10／使用者停止。
- 放鍵失敗或未取得同回合暫停確認時，不允許 AI／答案輸入；本回合截止仍繼續。
- 暫停途中再次取消、視窗關閉、移動、失焦或 deadline 到期，不重新按下原按鍵。
- AI acknowledgment、辨識回應及恢復資格均綁 round ID／generation；舊回合不能解鎖新回合。
- OCR 命中後的收圖、放鍵、等待 AI、輸入、確認及消失檢查都在同一個 30 秒期限內；不能在暫停完成時重設 t0。
- 原生輸入前後的檢查不能撤回已交給作業系統的事件；如實保留此限制。

## 11. 測試與打包驗收

採 RED→GREEN，至少涵蓋：

1. 長按 10 秒在第 3 秒收到圖片请求：先 key-up，才 AI／答案輸入；成功後再 key-down，只完成剩餘 7 秒。
2. delay 與 wait timeout 不扣解題時間；亂數時長只抽一次；巢狀迴圈／子腳本不重頭執行。
3. 一般、game、message、scan-pulse 模式的單鍵／組合鍵中斷皆不漏 key-up，暫停期間無 auto-repeat。
4. 已發出的文字前綴、點擊次數、短點按不重播；舊視覺座標在暫停後作廢。
5. 拖曳中斷會放開滑鼠，已開始拖曳的情況解題後停止，不自動重拖。
6. 未取得暫停確認，OCR 命中但 AI 呼叫仍為零；Discord 已派送且每回合一次，慢通知不阻塞交接。
7. 多次暫停／多個回合的交接隔離，舊 acknowledgment 不生效；停止旗標不曾被清除。
8. F10、失焦、幾何改變、按鍵釋放失敗、25／30 秒截止、晚到結果均不得復按或多送事件。
9. 沒有啟用圖片模式時，原動作、聊天、CLI、規則及 sleep 行為不變；兩種圖片設定模式皆可運作。
10. INFO 真正 start 才印、只印一次、有區域及 Discord 設定狀態，未啟用不印，無敏感 URL。
11. Windows 完整套件通過，再以既有 spec clean build；檢查模組收錄、包內 INFO、孤立資料目錄 GUI 啟動／正常關閉、來源及成品雜湊；備份舊 exe 後替換。

實機另外驗證遊戲的長按恢復行為、原生呼叫延遲、DPI／IME、F10、OCR／AI 與 Discord 實際服務。自動化測試不宣稱這些已驗收。
